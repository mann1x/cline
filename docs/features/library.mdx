The **Library** holds what you want the model to be able to look things up in: ebooks, manuals, papers, notes, web pages. It is arranged like a library: **sections**, **shelves** in each section, and **books** on the shelves. The model searches it and gets back the passages that answer a question, each with the book and chapter it came from. With the librarian turned on, the model also runs it: it catalogues what you give it, puts each book on the right shelf, and tells you when a book is already there.

The Library is **off by default**, is kept in Cerebriline's data folder, and is the same in every workspace: a book added while working on one project is there in the next.

## Turning it on

Open **Settings > Library** and tick **Enable the Library**. It applies from the next task.

The model then has two tools:

| Tool | What it does |
| --- | --- |
| `search_library` | Returns the passages that best match a question, best first. It can be limited to shelves or to books. |
| `list_library` | Shows the sections and shelves, the books on a shelf, or one book in full: what it is and what it was made from. |

These read the Library and never change it. Changing it is the librarian's.

## Sections, shelves and books

A **book** is whatever was put in it, and it need not be one file:

- the **original files**, copied into the Library and named by their sha256, so a file is recognised whatever it is called;
- the **text** read out of each, which is what is searched;
- the **pictures** taken out of the files, each with a description when a vision model is set;
- a **description** of the book, and what is known about it: authors, edition, year, language, ISBN, publisher, tags;
- for a book made from the web, the **query** it was made for and the **links** it started from.

All of it is in one folder per book, with a `book.json` that says what the folder holds. The folder is the book: it is what an export carries.

## The librarian

Tick **Let the model act as librarian** in **Settings > Library**. That turns on the built-in `librarian` skill and gives the model the tools that change the Library:

| Tool | What it does |
| --- | --- |
| `library_check` | Reads files, or takes links or a title, and says for each whether it is already in the Library. Changes nothing. |
| `library_add` | Makes one book from files, or adds files to an existing book. Makes the section and shelf if they are missing. |
| `library_organize` | Creates, renames, moves and deletes sections, shelves and books; merges two books; takes a source out of a book and puts it back. |
| `library_transfer` | Exports and imports. |
| `web_scrape` | Searches the web, lists a site's pages, reads one page. Only with [web scraping](#books-from-the-web) set up. |
| `library_web_book` | Makes a book from web pages, checks it for news, updates it. Only with web scraping set up. |

Then ask for it in plain words:

> Act as a librarian: catalogue the ebooks in `~/Downloads/ebooks` and add them to the Library.

The librarian looks at what shelves there are, reads each file, and for each one that is new works out its title, authors and edition, writes a short description, picks the shelf it belongs on (making a shelf or section only when none fits) and adds it. At the end it reports what went where and what it skipped.

Files are read by the [Document Reader](/features/document-reader): PDF, Word, PowerPoint, Excel, OpenDocument, RTF, HTML and ebooks (EPUB, MOBI, AZW3, FB2). Text and Markdown are taken as they are.

### Is it already there

Before anything is added, each file is compared with what the Library holds, in four ways:

| What matches | What it means |
| --- | --- |
| The same file, byte for byte | A duplicate. It is skipped. |
| The same ISBN | The same edition in another file or format. |
| The same title, or title and author | The same book or another edition of it. |
| Most of the text | 90% and more in common is the same book in another file. Less than that is another edition, a revision or another translation. |

The text comparison needs no model: each book has a fingerprint of its text, so the same book as a PDF and as an EPUB is recognised though no byte of the two files is the same. The files of one request are compared with each other as well, so a folder that holds the same book twice is told so before anything is added.

When a file looks like **another version** of a book that is there, the librarian adds nothing and asks you: keep both, or replace the old one. Replacing moves the old book to the trash.

### Pictures

A book's pictures are always taken out and kept with it. With **Describe the pictures of a book as it is added** on, each is described by a vision model and the description becomes part of the page the picture is on, so a figure can be found by what it shows.

**Profile whose model describes them** picks one of the profiles saved in the API configuration: a cheap, fast model that reads images is the right choice, since every picture is one request. With no profile picked, the model on the **Vision** tab is used; with none there either, pictures are kept without a description. **Pictures described per file** (40) limits how many of one file's pictures are described.

### Describing the pictures later

A book added while no vision model was set has its pictures and no descriptions: at most the caption the book gave them. Set the vision model, then ask the librarian to describe the pictures of the book. It uses `library_organize` with the action `describe_pictures`, which does not read the book again: the pictures are already in the book's folder. Each one is shown to the vision model, and what it says is kept with the picture and written into the book's text beside it, after the caption when there is one, so the picture is found by what it shows.

One call describes up to **Pictures described per file** pictures (or the `limit` it is given) and says how many are left; asking again goes on from there. A picture the model has already described is not asked about twice. Every picture is one request to the vision model, so a scanned book, where each page is a picture, is as many requests as it has pages.

### Watching an import, and cancelling it

Reading a book takes minutes: every page of a PDF, and every scanned page through text recognition. While `library_check` or `library_add` runs, its row in the chat shows one line per file: waiting, where it is (`page 312 of 769, recognizing text, 705 pictures`) and for how long, done with what it came to, or failed with the reason. A file that has not moved for a minute says **NOT MOVING** and for how long.

**Cancel import**, on the same row, ends the call. It ends as a failed tool call, and the model is given the whole report: which files were read, which were not, where the one in progress had got to, and whether anything reached the Library. The run goes on, so the model tells you and asks what to do next.

`library_web_book` shows the same with a line per link: how many pages of a crawl are read so far, and when it is cancelled a new book with no page stored is not kept.

Every call ends with that report, cancelled or not. It lists each file and, under it, everything that was left out of it with the reason: a scanned page whose text could not be recognized, a picture that could not be decoded or got no description. A book added to the Library is read whole: every scanned page is recognized, not the first forty an ordinary `extract_document` call reads.

The same lines go to the log once a minute, so a call that stops moving leaves a record of the file and the page it stopped on.

### Nothing is deleted by the model

A book the model deletes goes to the **trash**. So do the books on a shelf or in a section it deletes, and a source it takes out of a book. They stay there for **30 days**, out of every search, and can be put back by the model or by you. After 30 days they are deleted.

Emptying the trash, and deleting one book from it for good, is in **Settings > Library** only. The model has no tool for it.

## Books from the web

The librarian can make a book from web pages:

> Create a book on GitHub recipes for Godot development, call it Godot-Github.

It searches for the topic, chooses the links that are about it, reads them and makes the book. Or give it the links yourself. Either way the book keeps the **query** and the **links**, which is what lets it be brought up to date later, and what stops the same book being made twice:

> Is there anything new for Godot-Github?

reads the book's links again and lists the pages that are new or have changed, without changing the book. *"Update it"* brings them in. A page that no longer exists stays in the book.

A page counts as changed when its text has: a page that differs only in a view counter or a date does not, and a page that looks changed is read a second time before it is reported, because a page caught half loaded reads like another text.

This needs a [Firecrawl](https://github.com/firecrawl/firecrawl) endpoint, which reads pages in a real browser, so pages built by JavaScript are read too. Two switches, both needed, because pages are fetched from the open web on your behalf:

1. **Settings > Features > Web scraping for the librarian**: the endpoint's address, its key if it needs one, and how far a crawl may go. **Check** reads one page and shows what came back.
2. **Allow web scraping**, in the API configuration.

Without both, the two web tools are never offered to the model, librarian or not.

| Setting | Default | |
| --- | --- | --- |
| Pages one book may read in a call | 100 | The librarian asks for a page count per book; this is the most it gets. |
| Links deep a crawl may follow | 3 | 0 reads only the links given. |

Pages are asked for as HTML and converted to Markdown by Cerebriline, which keeps fenced code blocks and their language. Firecrawl's own Markdown loses them.

## The shelves in Settings

Once the Library is on, **Settings > Library** shows the shelves: each section, its shelves with how many books they hold, and under an opened shelf its books. Everything the librarian can do can be done there by hand:

- **New section**, **New shelf**, and **Rename** on each.
- A shelf is moved to another section, and a book to another shelf, with the dropdown beside it.
- **Details** on a book shows its description, the folder it is kept in, how many pictures it has and how many are described, and its sources, each with **Remove** or **Restore**.
- **Delete** asks once more, and sends to the trash.
- **Trash** lists what was deleted, where it stood, and the day it is deleted for good, with **Restore**, **Delete** and **Empty**.
- Problems are listed under the shelves: a book with no sources, a file missing from a book's folder.

## Export and import

**Export all…** writes the whole Library to one file. **Export** on a section, a shelf or a book writes just that. **Import…** reads such a file in: sections and shelves are made where they are missing, and a book that is already there is left alone. The librarian does the same with `library_transfer`, and can also replace an existing book or bring the file's in beside it as a copy.

The file is a gzipped tar of the books' folders: the original files, their text, pictures and descriptions, and where each book stood. **Vectors are not in it.** They are made again where the file is imported, with the embedding model set there, so a file exported with one model works in a Library that uses another.

## The search engine box

At the top of **Settings > Library**, once the Library is on, a box says where search stands: how many books, sources and passages are stored, whether LanceDB is downloaded and loads, its version, the embedding model in use and how many documents have vectors. **Download LanceDB** fetches it. Enabling the Library alone does not download anything: keyword search needs nothing.

## Choosing and checking the embedding model

On the **Embedding** tab of the API configuration, the model is picked from the server's own list when it gives one. An Ollama or xOllama says which of its models embed, so the list holds those only. Any other server lists all its models, with nothing to tell a chat model from an embedding one, and the tab says so. **Type a name…** is always there.

**Check the embedding model** embeds one sentence and shows what came back: the address that was used, whether it was the session's provider, the size of the vectors, or the server's refusal. Use it after ticking **Embed on the session's provider**: a server can list a model and still refuse to embed with it. **Check the reranking model** does the same with two passages and a question.

Nothing is embedded until a model is named. The search engine box in the Library and Memory panels says which one thing is missing: the box, the address, or the model.

## Changing the embedding model

Vectors from two models cannot be compared, so each embedding model has its own set of vectors, and so does each vector size of the same model. Changing the model does not break search: it starts a new set, and until that set is filled the documents are found by keyword only.

- **Embed N documents now**, in the search engine box, fills the set for the model now set. It shows its progress, and if it stops (a server that went away), what was done is kept and running it again carries on. Left alone, documents are embedded the next time one is added.
- **Vectors on disk** lists every set with its model, vector size, count and space. A set not in use is kept, so going back to its model needs nothing. **Delete** removes one; its documents are embedded again if its model is ever set again.
- The same model returning vectors of another size, after a tag was pulled again for instance, is noticed at the next search or check, and its documents are then counted as waiting.

The Memory panel has the same box for the notes.

## Search by keyword

With nothing else configured, the Library is searched by keyword. This needs no model and no download, works the moment a document is added, and is very good at names, codes and exact phrases. Words that appear almost everywhere in the Library are left out of a query, since they say nothing about which passage is wanted.

## Search by meaning

A keyword search cannot find a passage that answers a question in different words. An **embedding model** can.

1. In **Settings > API Configuration**, tick **Use an embedding model**.
2. On the **Embedding** tab that appears, name the model, and either tick **Embed on the session's provider** or type an endpoint.

Any server that speaks the OpenAI embeddings API works: Ollama, opencoti, llama.cpp, LM Studio, or a hosted service. On Ollama, for example, `snowflake-arctic-embed2`, `bge-m3`, `qwen3-embedding:0.6b` or `nomic-embed-text`.

The first time the box is ticked, Cerebriline downloads **LanceDB**, the database the vectors are kept in. It is 200 to 390 MB depending on your platform, is fetched once, from the npm registry, into Cerebriline's data folder, and each file is checked against a known checksum before it is used. It is not available on Intel Macs; there the Library stays on keywords.

Documents are embedded when they are added. Documents that were added before an embedding model was set are embedded the next time something is added. If embedding is interrupted, it continues from the document it stopped at.

Changing the embedding model keeps the vectors already made and starts a new set, because vectors from two models cannot be compared.

## Reranking

A **reranking model** reads each of the best passages together with the question and scores how well it answers. It is slower than the search and far better at putting passages in order.

On the Embedding tab, tick **Use a reranking model** and name the model and its endpoint. Cerebriline calls `POST <endpoint>/rerank`, which llama.cpp (`llama-server --reranking`), opencoti, Jina, Cohere and text-embeddings-inference serve. `bge-reranker-v2-m3` is a good general choice.

<Note>
Ollama has no rerank route. A reranker pulled with Ollama has to be served by one of the servers above. With llama.cpp, start the server with a batch as large as its context (for example `-c 8192 -ub 8192`): its default batch of 512 tokens is smaller than a passage, and Cerebriline then gives the reranker only the beginning of the longer passages.
</Note>

Reranking also works without an embedding model, over the keyword results.

## Settings

All in **Settings > Library**.

**Splitting documents.** A document is cut into passages, and passages are what is searched and returned.

| Setting | Default | |
| --- | --- | --- |
| Passage size is measured in | Characters | Or tokens, estimated. |
| Split at headings first | On | A passage does not run across a heading, and keeps the headings it sits under. |
| Passage size | 1500 | |
| Overlap | 100 | Repeated at the start of the next passage, so a sentence cut at the border is whole in one of them. |
| Smallest passage | 0 | Shorter passages are joined to a neighbour under the same heading. 0 is off. |

These apply to documents added from then on. Add a document again to split it anew.

**Searching.**

| Setting | Default | |
| --- | --- | --- |
| Hybrid search | On | With an embedding model, search by keyword and by meaning and merge the two. Off, by meaning alone. |
| Match file names, titles and headings too | On | A keyword also counts in the document's name and the headings above a passage. |
| Balance | 50% / 50% | How much each ranking counts when they are merged. |
| Passages kept from the search | 5 | |
| Passages kept after reranking | 3 | |
| Relevance threshold | 0 | Passages the reranker scores below this are dropped. 0 keeps them all. |

**Requests.** How many passages go in one embedding or reranking request, how many embedding requests run at once, and a prefix for questions and for passages, for the embedding models that were trained with one (`query: ` and `passage: ` for the E5 family). Leave the prefixes empty unless the model's card asks for them.

## In the CLI

`--library` offers `search_library` and `list_library`. `--librarian` adds the librarian's tools. The embedding model is named by `CLINE_EMBEDDING_BASE_URL` and `CLINE_EMBEDDING_MODEL`, the scraping endpoint by `CLINE_SCRAPE_BASE_URL` (and `CLINE_SCRAPE_API_KEY`, `CLINE_SCRAPE_MAX_PAGES`, `CLINE_SCRAPE_MAX_DEPTH`), and pictures are described by `--vision-model`.

## What it does not do yet

- Books are added by the librarian, on request. There is no file picker in the panel; the panel imports an exported file.
- A book made from the web is checked for news when you ask. Nothing checks on a schedule.
- Scanned pages are read with the Document Reader's OCR, which reads a limited number of pages per document.
- A Library from before it had shelves keeps its documents: each old collection becomes a shelf in a section named **General**, holding one book. Those books record where their files were and do not hold a copy of them.
