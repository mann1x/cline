**Memory** lets the model keep notes between tasks, so what it worked out once does not have to be worked out again: a decision and its reason, how the project is built and tested, a convention, something you said you prefer, a trap that cost time.

Memory is **off by default**. Notes are kept in Cerebriline's data folder, not in your project, so nothing is added to the repository.

## Turning it on

Open **Settings > Memory** and tick **Enable Memory**. It applies from the next task.

The model then has three tools:

| Tool | What it does |
| --- | --- |
| `remember` | Keeps one note, with a few tags to find it by, in the memory this workspace stores to. |
| `recall` | Returns the notes that best match a question, best first, each with its id, date, memory and tags. With no question it lists the newest notes. |
| `forget` | Removes a note by its id, when it no longer holds. |

You can simply say so: *"remember that we run the tests with node --test, not jest"*, *"what do you know about how this project is deployed?"*, *"forget the note about the staging server"*.

## Automatic recall

With **Recall automatically** on, which it is by default, Memory is searched with every message you send, at the start of a task and after it. The notes that are about the message are put beside it for the model, so they arrive without the model having to ask. Small models seldom call `recall` on their own.

You see one line in the chat, for instance *Recalled 2 notes from Memory (m3, m1)*. The model sees the notes themselves, marked as noted in earlier tasks and to be checked before they are relied on.

- A note is given to a task once. If the conversation is compacted later, the model can still call `recall`.
- A message shorter than 12 characters ("yes", "continue") is not searched with.
- A search that fails, or a server that is down, never holds up a message: it goes to the model without notes.

A search always returns its best matches, however poor. So a note is attached only when something says it is about your message:

| With | A note is attached when |
| --- | --- |
| Keyword search only | it shares at least two meaningful words with the message |
| An embedding model | the above, or it is close to the message by meaning |
| A reranking model | the reranker scored it at or above the **relevance threshold** |

The model still has `recall`, and its own searches are not filtered this way: it asked.

### Expanding the question (HyDE)

A message and the note that answers it often share no words: *"how do I check my changes before I commit?"* against *"tests are run with node --test"*. With **Expand the question first (HyDE)** on, a second model writes the short note that would answer your message, Memory is searched again with that, and the two results are merged.

The hypothetical note is grounded: the second model is given the notes the first search returned, or the newest notes when it returned none, and told to use only what is in them. Asked to imagine a note about a project's own names from nothing, a model invents one about something else.

Pick the model under **Profile whose model writes it**: one of the profiles saved in the API configuration. Its provider, model, window and sampler are used; the key is the one stored for that provider. It adds one short model call to every message, so a cheap, fast model is the right choice, and a small cloud model is the usual one.

- Until a profile is picked, Memory is searched with your message alone.
- The call has 20 seconds. If it fails, is empty or runs out of time, the first search stands.
- The same message with the same notes is not expanded twice in a session.

HyDE (Hypothetical Document Embeddings) is from Gao, Ma, Lin and Callan, *Precise Zero-Shot Dense Retrieval without Relevance Labels* (2022). The order of work here (search first, expand grounded on what was found, search again, merge) is the one [claude-hooks](https://github.com/mann1x/claude-hooks) uses.

## Memories

There can be any number of memories. They are all kept in one place, Cerebriline's data folder, and **Settings > Memory** lists every one of them whichever workspace is open.

- **Main** is there from the start and cannot be deleted. Every workspace starts on it, for storing and for recall.
- Any other memory is one you make: for a workspace, for a client, for a topic, or imported from a file.

For the workspace that is open, the list has two columns:

| Column | What it sets | How many |
| --- | --- | --- |
| **Recall** | The memories this workspace's tasks may search. | Any number |
| **Store** | The memory new notes are kept in. | Exactly one |

The choice is kept per workspace. The model's tools take no memory name, so a model cannot read from, or write to, a memory that is not ticked for its workspace. `forget` removes a note only from the memory the workspace stores to; a note in a memory that is only read is yours to remove.

When the open workspace has no memory of its own, the panel offers **Create a memory for this workspace**, named after the folder. A memory made that way is ticked for recall; where notes are stored stays as it was until you move it.

A workspace is its folder path. The same repository opened from another folder is another workspace, and starts on Main.

### Export and import

**Export** writes a memory to a `.memory.json` file: the notes, their tags and the day each was noted. **Import…** reads such a file into a memory of the file's name, making it if it is not there. A note already present is left alone, so reading the same file twice adds nothing. Vectors are not in the file; they are made again where it is read.

### If you used Memory before this build

The first build had a global part and a part per workspace. They are brought over the first time Memory is opened: the global part is **Main**, and each workspace's part is a memory named after its folder. Those are not ticked for recall automatically. Tick them for the workspaces that should see them.

## How notes are found

By keyword, with nothing to download and no model to configure.

The **Search engine** box at the top of the panel says where things stand: how many notes are stored, whether LanceDB (which holds the vectors) is downloaded and loads, its version, the embedding model in use, and how many notes have vectors. **Download LanceDB** fetches it (200 to 390 MB, depending on the platform). Ticking **Use an embedding model** in the API configuration fetches it too; enabling Memory alone does not.

To find notes by meaning as well, tick **Use an embedding model** in the API configuration and name the model on the **Embedding** tab. Memory and the [Library](/features/library) share that tab: one embedding model and one optional reranking model serve both, and both use the same LanceDB download. A note kept before an embedding model was named is found by keyword until the next note is kept, which embeds the ones still waiting.

## Settings

| Setting | Default | What it does |
| --- | --- | --- |
| Enable Memory | off | Offers the three tools. |
| Recall / Store, per memory | Main for both | Which memories this workspace searches, and the one it stores to. |
| Recall automatically | on | Searches Memory with every message you send and gives the model the notes about it. |
| Expand the question first (HyDE) | off | Has a second model write the note that would answer the message, and searches with that as well. |
| Profile whose model writes it | none | The saved profile used for the expansion. |
| Notes a recall returns | 5 | The most notes one recall gives the model. Each one takes room in the conversation. |
| Relevance threshold | 0 | With a reranking model, notes scored below this are left out. 0 keeps them all. Without a reranker it has no effect. |

## Limits

- A note is at most 4,000 characters and is kept whole; it is not cut into passages.
- The same note kept twice in the same memory is kept once.
- Notes are not synced between machines. They live in the data folder of the machine that made them.
- The panel lists memories and counts their notes, not the notes themselves. Ask the model: *"list your notes"*.
- A memory cannot be renamed yet. Export it, import it under the new name, and delete the old one.

## In the CLI

`--memory` (or `CLINE_MEMORY=1`) offers the same tools on the panel's defaults, on the main memory unless `CLINE_MEMORY_STORE` names another to store to and `CLINE_MEMORY_RECALL` a comma-separated list to search, with automatic recall; `CLINE_MEMORY_AUTO_RECALL=0` turns that off. `CLINE_MEMORY_HYDE_MODEL` names a model on the session's provider to write the expansion. An embedding model is named by environment: `CLINE_EMBEDDING_BASE_URL`, `CLINE_EMBEDDING_MODEL` and, where the endpoint needs one, `CLINE_EMBEDDING_API_KEY`. Notes are kept under `--data-dir`.
