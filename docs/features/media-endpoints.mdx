A media tool sends its request to a server that speaks OpenAI's media routes. Today these are `generate_image`, `edit_image`, `transcribe_audio` and `synthesize_speech`. Video generation is planned and will use the same rule.

## Images

Tick **Use an endpoint for image generation and editing** on the API configuration panel, then fill in the Images tab.

| Tool | What it does | Route |
|---|---|---|
| `generate_image` | Makes an image from a description and saves it into the workspace. | `POST <endpoint>/images/generations` |
| `edit_image` | Changes an image already in the workspace by instruction and saves the result as a new file. It takes one or more images (the first is edited, the rest are references) and an optional mask. | `POST <endpoint>/images/edits` |

Edits go where generation goes. To send them elsewhere, name an **Edit endpoint** or an **Edit model** on the tab; the tab's one API key is sent to both. Untick **Also offer image editing** to keep `generate_image` without `edit_image`.

How far an edit goes depends on the model. An instruction-edit model such as FLUX.2 klein or Qwen-Image follows the prompt. A plain diffusion model redraws over the source and makes smaller changes.

## Audio

Tick **Use an endpoint for audio processing** on the API configuration panel, then fill in the Audio tab. It holds two endpoints, because speech-to-text and text-to-speech are often two servers. Each has its own URL, API key and model, and its own switch.

| Tool | What it does | Route |
|---|---|---|
| `transcribe_audio` | Turns an audio file in the workspace into text. It can return plain text, or write subtitles (`srt`, `vtt`) or the timed segments (`verbose_json`) to a file. It can also translate to English. | `POST <endpoint>/audio/transcriptions`, or `/audio/translations` |
| `synthesize_speech` | Turns text into an audio file in the workspace. | `POST <endpoint>/audio/speech` |

The Audio tab also sets a **Default voice** and a **Default format** for calls that name none. Open the voice field to list the engine's voices. Only opencoti and xOllama can list them, and xOllama starts the speech engine to answer, so the list is fetched when you open the field and not before. For any other server, type the voice name.

Audio is never re-encoded. The file is named from the bytes that come back, so asking for `mp3` from an engine that only encodes WAV gives a `.wav` file. An engine that refuses the format asked for is asked once more for its own default.

## Which server a tool uses

Each media tab on the API configuration panel has a checkbox, **Use the session's opencoti or xOllama provider when it …**, and an endpoint of its own (URL, key, model). When a session starts, each tool is resolved in this order:

1. **The session's provider**, when the box is ticked, the provider is an opencoti or xOllama server, and that server serves this kind of media. One opencoti process can serve the chat model and every media engine at once, and an xOllama model can carry media engines.
2. **The typed endpoint**, when the session runs on any other provider, or on an opencoti or xOllama that does not serve this kind.
3. **No tool.** If the typed URL is empty or has no model, the tool is not offered and the model is never told it exists.

A typed endpoint that is down, or that says it does not serve this kind, is still offered: these servers may be started on request. The tab shows a warning, and a call made while the server is down tells the model so. To stop offering a tool, untick its "Use an endpoint for …" box.

The tab shows which of these applies now, and why a tool is not offered.

## How a server is recognised

| Server | How it is recognised | How it says what it serves |
|---|---|---|
| opencoti | `GET /props` carries a `features` array | `images_generate_v1`, `images_edit_v1`, `audio_transcriptions_v1`, `audio_speech_v1`, `videos_generate_v1` |
| xOllama | `GET /api/xollama` answers | each media model's `/v1/models` row lists `capabilities` and its input and output modalities |
| anything else | `GET /v1/models` answers | it does not say; it is taken to serve what it is asked for |

On opencoti and xOllama a kind the server does not list is treated as not served. On any other server nothing is assumed either way.

## Choosing the model on the session's provider

The model field on the tab names the model. If it is empty, the session's own model is used when it serves the kind, and otherwise the only model that does. When several models serve the kind and none is named, the tool is not offered and the tab says so.

## When an engine is busy

opencoti and xOllama run one request per engine and answer `503` with `Retry-After` to the rest. The tool waits and asks again, for up to 30 minutes, and reports only then that the engine is still busy. Other refusals are not retried: `400` means the model does not do this, `404` means no such model, and `500` means the engine failed.

The time limit on a request (3 minutes for an image) counts the work, not the time spent waiting in the queue.
