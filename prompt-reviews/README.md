# `prompt-reviews/` — layout and rules

This directory holds the model-written prompt templates: the set we currently
believe is best, every run that produced a candidate, and the backups taken
before a regen overwrote anything.

It is **not** a shipping location. Nothing here is loaded at runtime. The
templates the product uses live in
`sdk/packages/core/assets/prompt-templates/`, and getting a file from here to
there is a deliberate copy plus a bundle rebuild — see
`sdk/packages/core/src/extensions/config/PROMPT-TEMPLATES.md`.

## The layout

```
prompt-reviews/
├── README.md                  ← this file
├── <family>.md                ← THE CURRENT SET. One per family. Nothing else.
├── regen/
│   └── <YYYYMMDD-HHMM>-<model>/
│       ├── <model>.md         ← what that model proposed, in that run
│       └── run.log            ← the audit trail for that proposal
└── archive/
    ├── templates-backup-<YYYYMMDD-HHMM>/   ← the shipped set, before a regen
    └── superseded-<YYYYMMDD>/              ← what the root held before it
```

### Three rules, and why each one exists

**1. The root holds current templates and nothing else — one file per family,
named for the family.**

Not for the model that wrote it. `prompt-template-parser.ts:230` falls back to
the filename when frontmatter omits `name:`, so `minimax.md` *is* the template
named `minimax` — the filename is identity, not decoration. A root full of
`glm-5.2-cloud.md` and `qwen3.5-397b-cloud.md` also cannot answer the only
question the root exists to answer: which template is current for this family.
Two files claiming one family is a directory that has stopped being an answer.

**No logs in the root.** A log belongs to the run that wrote it, and a run is a
directory.

**2. Every run writes to `regen/<YYYYMMDD-HHMM>-<model>/`, and writes its own
log there.**

The generator does this on its own — `review-prompt-templates.mts` computes one
stamp per invocation and one directory per model, and writes `run.log` beside
the `.md` itself. That is deliberate: the five logs that used to sit loose in
the root got there because the path was typed into a shell redirection per
invocation, so it was correct only when someone remembered. `--out` overrides
the *root* (`prompt-reviews/regen`); there is no flag that drops a proposal
loose in a directory.

Naming a run for its purpose — `regen-20260911-gated`, `-pass2`, `-glmflash2` —
is what made seventeen directories unreadable within a day. The date orders
them and the model identifies them; the purpose belongs in the log.

**3. `archive/` holds backups, and a regen takes one first.**

Back up the *shipped* set — `assets/prompt-templates/` — into
`archive/templates-backup-<stamp>/` before regenerating, because the reason to
keep it is the case where the new templates turn out to be worse. Retiring the
root's current set puts it in `archive/superseded-<date>/`.

Archive is append-only in practice. Nothing here is large.

## Running a regen

```bash
cd sdk/packages/core
cp -r assets/prompt-templates ../../../prompt-reviews/archive/templates-backup-$(date +%Y%m%d-%H%M)
npx tsx scripts/review-prompt-templates.mts --all
```

Proposals land in `prompt-reviews/regen/<stamp>-*/`. The script copies nothing
anywhere and says so when it finishes. Read the proposals, and promote the ones
that are better:

```bash
cp regen/20260911-0611-glm-5.2-cloud/glm-5.2-cloud.md glm.md
```

Then record which run it came from in the table below — a template in the root
with no provenance is one nobody can re-derive, which is the whole reason this
directory exists.

## Provenance: the header is written by the script, never by the model

Every template in the root opens with a `<!-- PROVENANCE -->` block naming the
model that wrote it, the family that model reported, the run directory, and both
samplers in play.

**Nothing used to write it.** The header was model-written: the generator hands
a model its current template, that template opens with a provenance comment, and
the model copies the comment into its reply. So the line was inherited, not
observed -- and therefore wrong exactly when it mattered. Measured 2026-09-11:
`deepseek.md` was generated by `deepseek-v4.1-flash:cloud` against a live
`family=deepseek_v41` and came back claiming `deepseek-v4-flash:cloud`, family
`deepseek4`. In the same run six of eight proposals carried no header at all,
because a model that rewrites the opening of a file simply drops it.

`review-prompt-templates.mts` now strips any model-supplied header and stamps
its own from the model id it called and what `/api/show` reported. A model
cannot report which model it is; the caller always can.

**Both samplers are recorded**, because a template is prose and prose is a
sampled output. The generator asks for `temperature 0.2`; every key it does not
set falls through to the tag's own sourced parameters. Cloud tags report none --
their sampler is server-side and invisible to `/api/show`, which the header says
in as many words rather than implying the model ran bare. Local overlay tags
(`igovet/...`) report a full set, and those values are why the overlay exists.

## Auditing a template in the root

The flag depends on how the template matches, and getting it wrong reads as a
failure:

```bash
cd sdk/packages/core
# family-matched: gemma, qwen, kimi, glm, deepseek
npx tsx scripts/audit-prompt-template.mts ../../../prompt-reviews/glm.md --family glm5.2
# model-matched: claude, minimax, nemotron
npx tsx scripts/audit-prompt-template.mts ../../../prompt-reviews/minimax.md \
  --model igovet/minimax-m3-opencode:latest
```

Without the right flag the auditor reports *"The `match:` block no longer selects
this model (family 'unknown')"* -- which is the flag missing, not the template
being broken. All eight are clean at 34/34 sections as of 2026-09-11.

working.

### The kimi split

`kimi-k3.md` was added at `family: [kimi-k3*]`. `kimi.md` **keeps**
`family: [kimi*]` and is the fallback rung: pattern specificity ranks the
narrower pattern above the generic one inside the `family` dimension, so both
ship and order does not matter.

| tag | family | params | resolves to |
|---|---|---|---|
| `kimi-k2.6:cloud` | `kimi-k2` | 1.042T | `kimi` |
| `kimi-k2.7-code:cloud` | `kimi-k2` | 1.042T | `kimi` |
| `kimi-k3:cloud` | `kimi-k3` | 2.812T | `kimi-k3` |
| *a future* `kimi-k4` | `kimi-k4` | — | `kimi` |

**2.6 and 2.7-code cannot be separated by family** — same string, same parameter
size — so they share `kimi.md`. Separating them would need `model:` patterns on
the exact tag names.

Do not narrow `kimi.md` to `kimi-k2*`. That removes the bottom rung and a future
generation falls silently to `default.md`, which is the failure that hit `glm5*`
and `deepseek4*`.

## Why so many runs on 2026-09-11

Twenty-eight, for eight templates. Four cloud tags moved under us, two models
needed a params-only overlay before they would produce a whole template at all,
and the required-guidance gates rejected two correct answers over phrasing
before the patterns were widened. The runs are all kept: the ones that failed
are how the overlay technique and the gate-width rule are documented at all.
