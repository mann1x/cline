## A settings field that could not get an answer said the wrong thing

The Parallel Sessions box on an opencoti profile showed "Default: 1" and a
description written for a server with a fixed slot count — on a server whose
PolyKV admission gate was on and which decides for itself. Asked directly:
leave it empty. Empty and `0` are the same thing, and on this server they mean
the engine decides.

The panel was not wrong about the server; it never got an answer. It asks one
read, and that read waits on `GET /polykv/tps`, which on this engine answers
its headers with a `200` and then never ends the body — measured on two ports,
so it is the server and not the tunnel in front of it. Every read in that
client was unbounded, so the question simply never came back, and the field
fell to the copy it shows when nothing is known.

Those reads have a bound now. The request is cancelled rather than abandoned,
so a hung poll does not leak a socket; the wait is bounded separately as well,
because the read that hung delivered its headers promptly and only the body
never arrived. Five seconds, against a `/props` that answers in 70ms.

`/props` is the one that mattered more. It is read at session start to decide
how many agents may run at once, so the same hang would have stalled a session
rather than a panel.

## Nothing to save is not a failure to save

Clearing the box and finding no Update offered was the field already being
empty. The host's own log has the moment it took effect:

    15:44 [Agents] Concurrency: 1 — opencoti has PolyKV admission on, but
          this profile caps delegation at 1
    17:35 [Agents] Concurrency: uncapped — opencoti has PolyKV admission on;
          the engine decides, not a slot count

So the profile was already saying what it should. What made it look otherwise
was the placeholder above it claiming empty meant one.
