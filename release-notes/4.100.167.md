## One spawn queue for every node, several agents per call, and swarms on any node

- **A node with free room never sits idle while agents wait.** Every agent
  waits in one queue, oldest first. A node that is capped (a Parallel Sessions
  count) takes the head of the queue the moment one of its agents finishes. A
  node with no cap (an elastic or PolyKV opencoti) takes one agent, and the
  next only once the engine has started generating for that one. Before, an
  uncapped node "had room" by definition. In the 75-agent run the two opencoti
  nodes took all 75 at the start, and the ollama node finished its one agent
  in 66 s and then sat idle for the rest of the run.
- **A spawn that fails goes back to the front of the queue.** An agent refused
  before it started (a 429 from admission control, or the pool owner's window
  being full), or placed on a node that is unreachable or lacks the model,
  returns to the head of the queue and takes the next node with room. A
  refused node takes no one else until one of its agents finishes, or 5
  seconds pass. An agent that fails after it started is not re-run, because
  re-running would repeat what it already did.
- **`spawn_agent` takes a list.** `agents: [{name, task, instructions?, type?}]`
  runs several agents in one call, with `knowledge` and `instructions` stated
  once. Each agent still gets its own row, Stop, node and speed. `type` names
  a configured agent, which then runs with its own role and model. The lead
  in the 75-agent run wrote 75 separate calls, each repeating the same shared
  context, and dropped the configured agent types entirely.
- **Swarms are a mode of `spawn_agent`.** Set `merge: true` (with `count` for
  one repeated task) to run the agents as a swarm on a snapshot of your
  context, with one merged report back. There is no separate `spawn_swarm`
  tool, so every request carries one schema fewer.
- **Swarms are offered when any node has them.** Swarms used to appear only
  when the lead itself was on opencoti with its switch on. Now the lead's
  connection, the Agents tab, or any agent node can enable them, provided its
  own PolyKV switch is on and its engine confirms pools. Nodes without swarms
  still take swarm workers, as fixed-capacity nodes.
- **A node's PolyKV settings reach it.** A node's connection was built without
  its tab's PolyKV section, so swarm and pooling switches set on a node had no
  effect.
- **Fixed: the built-in template module was stale in 4.100.166.** A session
  using a template read the old `spawn_agent` text without the pacing note.
