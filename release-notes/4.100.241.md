## Built-in skills

Cerebriline now ships with skills of its own. They appear in the Skills tab
under **Built-in Skills** with nothing to install, in the extension, the CLI and
the SDK alike.

Fifteen to start with.

For deploying and running:

- **mandatory-qa-prompt-and-issue-resolution** (Chris) asks, after a change to
  code or configuration, whether to run QA on it, runs a QA plan fitted to the
  change and reports, then asks whether to fix what it found.
- **docker-compose-deploy** (Chris) deploys the open project to local Docker
  from its compose file or its Dockerfile, and verifies the deployment. Its
  commands now work in bash as well as PowerShell, and its reachability check
  waits for the app to come up.
- **build-project** builds the open project the way the repo defines, and its
  Docker image when it has one.
- **run-project** starts the open project, waits until it answers and opens it
  in the browser.

The last three refer to each other and are meant to be turned on together.

For test-driven development:

- **tdd-wizard** starts a project or a feature test-first. It learns about the
  project, takes your specification or writes one with you through questions
  about goals and scope, develops the test cases with you, then generates,
  validates and writes the tests. At the end it offers to carry on with the
  next phases or to leave them to you.
- **tdd-gen** writes the implementation that makes existing tests pass, without
  changing the tests.
- **tdd-test** runs the project's tests the way the repo defines and reports
  the failures.
- **tdd-coverage** measures coverage and proposes a test for each gap.

The TDD set follows the workflow in Duke Harewood's article
"[Test-Driven Development with Claude Code: Practical Guide](https://aiskill.market/blog/tdd-with-claude-code)"; each skill credits it.

For spec-driven development, after [Get Shit Done (GSD 2)](https://getshitdone.help/):

- **sdd-wizard** is the way in. It reads the project's planning files, says
  where the work stands and runs the next step, one at a time or, when asked,
  on its own until the milestone is done or something needs you.
- **sdd-discuss** turns an idea into an agreed specification: it reflects your
  vision back, reads the code, asks in short rounds, and writes the brief and
  the numbered requirements for you to approve.
- **sdd-plan** cuts a milestone into slices that can each be demonstrated,
  riskiest first, and a slice into small tasks that each name their files,
  their steps and the command that proves them.
- **sdd-execute** does one task, verifies it and writes down the evidence.
- **sdd-verify** closes a slice, writes and runs its acceptance script,
  reassesses the rest of the roadmap, and at the end audits the milestone
  against what was promised.
- **sdd-quick** is for a small change that needs none of that, and
  **sdd-status** reports where things stand.

The plan and its records live in a `.sdd/` folder in your project, so the work
continues in a new chat. With Subagents on, each task runs in an agent with a
fresh context and its changes are checked before they are adopted; with
Teammates on as well, independent slices can run side by side.

All ship turned off: turn on the ones you want. A built-in skill can be
switched on and off and opened to read, but not edited or deleted, since an
update replaces it. The switch is kept in your settings and survives updates.
To change what one does, create your own skill with the same name; yours
replaces it.
