## repeat_last_n offered a value the server rejects

Setting it to -1 made every request of the session fail with

    Field 'repeat_last_n': Value must be between 0 <= value <= 2147483647, but got -1

The field had no lower bound at all, and its description promised that -1
"uses the whole context". That is true of two engines and false of the third
— and the third is the one that answers 400 rather than interpreting it:

| engine | `-1` |
|---|---|
| Ollama | resolves to the context window |
| opencoti | allowed, means the context size |
| llama.cpp | **rejected** — its schema takes 0 and up, and 0 is the only special value it documents |

opencoti and llama.cpp are reached through the same OpenAI-compatible form,
so the form alone could not tell them apart. It can now: each engine gets the
range its own server enforces, and the description on screen matches the
engine you are pointed at. Nothing changes for Ollama or opencoti; on
llama.cpp the field starts at 0 and no longer claims otherwise.

Having no minimum was a second hole — `-2` was accepted everywhere too.

## An error that said "[object Object]"

A provider's rejection showed as `[object Object]` above the raw response,
which is where the actual sentence was. Errors that arrive shaped
`{"error":{"code":400,"message":"…"}}` carry no message at the top level, and
the message that got displayed was what stringifying the whole body produces.

The message is read out of the body now, and the fallback can no longer be
opaque. Two branches of the old chain could never run at all: it ended
`String(error) || error?.cause?.means`, and `String()` of anything is a
non-empty string, so nothing after it was ever reached.
