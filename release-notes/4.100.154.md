## The Agents tab holds nodes now, not one connection

Delegated agents ran on one endpoint: whatever the Agents tab named. A
fan-out could only ever be as wide as that one server, and a second machine
sitting idle beside it was unreachable.

The tab now carries a row of node tabs above the provider form. Node1 is
always there and cannot be removed — it is the tab exactly as it was, reading
and writing the same configuration, so nothing needs migrating and an empty
Node1 still means no agents at all. "+" adds a node, the trash removes it and
its configuration, and each node carries a priority.

Priority 1 is the highest. Agents are placed on the free nodes of the best
priority they can get, taking turns between nodes that share one; a lower
priority is used only when nothing above it has room. When every node is busy
the next agent waits rather than failing — and when a slot frees up higher, a
waiting agent goes back up to it rather than staying where it overflowed to.

The number on a tab is a position, not a name. Remove Node4 of six and the
last two read Node4 and Node5, while the configurations behind them stay
exactly where they were.

Each node asks its own endpoint how many agents it will serve at once, which
is the only sensible answer when two nodes are two machines.

On the CLI the same thing is a repeatable flag:

    --agent-node model=v9,url=http://host:8240,priority=1,capacity=4
    --agent-node model=v9b,url=http://other:8240,priority=2,capacity=2

## A profile loaded onto a second node replaced the first

The profile bar sits above the Agents tab rather than inside it, and knew
nothing about nodes. Standing on Node2 it showed Node1's provider and model,
and loading a profile there overwrote Node1's entire configuration — no
warning, no undo, and the tab you were looking at unchanged.

It follows the selected node now, and each node remembers which profile is
loaded on it separately. The same mistake in a quieter place is fixed with
it: two nodes on one provider shared a sampler entry, so the second silently
overwrote the first.

## A swarm no longer loses workers to a full session window

Workers in a swarm share the lead session's context window on the server. A
round wide enough to fill it got part of its fan-out refused outright, and the
digest came back missing that work with nothing saying why — on one measured
six-worker round, two workers were lost.

That refusal is not a failure: it is the engine saying the window is busy
right now, and a worker that finishes frees exactly the room the next one
needs. Refused workers wait and then run, and the wait is logged so a slow
round reads as a slow round.

## The swarm tool is not offered when the server cannot do it

`spawn_swarm` is now withheld unless the endpoint itself confirms pooling is
on, rather than being offered to any endpoint that looks like the right kind
of server. Its schema comes off the context window with it — worth about
1,400 tokens on every request of a session that could never have used it.
