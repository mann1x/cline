## Forty requested agents ran eight wide

The lead asked for forty agents in one message, across two uncapped PolyKV
nodes and a third capped at one. They ran eight at a time, each starting at the
millisecond another finished:

    ib6al1 ends +42.6  →  4lg67f starts +42.6
    avzh7u ends +44.6  →  zs1rg2 starts +44.6
    d6dboc ends +47.2  →  ndg8c6 starts +47.2

That is a semaphore releasing one slot at a time, and it was not the node
placement — two of the three nodes had no ceiling. Every tool call in one
assistant message goes through a pool of eight, and forty `spawn_agent` calls
are forty tool calls.

The pool is right for what it was written for: a batch of reads should not open
forty file handles because the model sent forty. It is wrong for delegation,
where concurrency already has an owner — the node placement queue, which holds a
node of capacity one to one, and past it the engine's own admission gate. The
pool sitting on top made both decorative.

Agents now start together and wait where their own gate says to. Every other
tool keeps the pool, and an explicit sequential setting is still one at a time
for everything. A session with no nodes is still held to its endpoint's slot
count: an empty Parallel Sessions field on a fixed server still means one.

## Why the lead did not use the swarm

`spawn_swarm` forks the lead's own live context from its PolyKV session, so it is
only offered when the *session's* model runs on an opencoti with pools on. A lead
on Ollama cannot have one, and forty `spawn_agent` calls across the nodes is the
correct way to fan out from it — that path is what this release fixes.
