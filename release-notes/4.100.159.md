## A node is called what the settings panel calls it

The chat says which node an agent ran on. It said it like this:

    Cerebriline used `subagent_js_syntactic` — on node-mucuczcm

That is the node's storage key, generated when the node is added and shown
nowhere in the panel, so the row named a machine you had no way to look up.
`primary` was worse than opaque: it reads as "the primary model", which is the
one thing it does not mean. It is Node1's id, and Node1 *is* the Agents tab —
the different-model configuration. So the badge appeared to say the session's
model had been used, on a run whose own log says the opposite.

The names existed all along. `Node1`, `Node2`, `Node3` are what the node tabs
have shown since nodes did; the runtime simply could not reach them. It carries
them now, taken from the stored list rather than the placed one — a node that
names no provider is dropped before placement, and renumbering around the gap
would call Node3 "Node2" on the one screen where you are telling them apart.

## The Parallel Sessions field stops waiting on a read it never needed

It asked which controller decides concurrency through the same host read the
PolyKV status strip uses, and that read waits on `/polykv/tps` — which on the
published engine answers its headers with a `200` and then never ends the body.
Bounded in 4.100.158, so it now answers in five seconds instead of never. Five
seconds is still the whole time the panel spends saying "Default: 1" on a server
whose admission gate is on.

The two questions have opposite costs. The strip wants pools, sessions and the
KV ledger, and pays for them. The field wants one boolean, and `/props` carries
it in 70ms and is cached per server afterwards. The field has its own read now.

Two things that probe could get away with while only session start used it, and
cannot now. Whether the server answered at all is a fact it reports rather than
one the caller infers — a plain llama.cpp server and a server that is not there
both have neither controller on, and what to say about them is opposite. And a
server that did not answer is no longer cached: caching an answer is the point
of the probe, and caching a failure is a panel that never asks again.
