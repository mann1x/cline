## Agents run on your nodes, in parallel, and the chat shows it

A run with three agent nodes configured spawned three agents in one batch and
they finished 80, 108 and 148 seconds apart, each starting only as the one
before it ended. They had all been launched together. Three separate things
were serialising them, and each one hid the next.

**Capacity `0` meant two opposite things.** The placement engine read it as
"this node is off, never use it"; the setting that resolves a node's capacity
returns `0` for "the endpoint's own admission control decides". So an elastic
or PolyKV endpoint with the Parallel Sessions box left empty — the
recommended setting — produced a node that was never placed on at all. The
two readings are spelled differently now, and leaving the box empty means
what it says.

**The delegation gate asked only the profile.** Whether `spawn_agent` and the
team tools are offered was decided from one number, this profile's parallel
sessions, so three nodes serving one request each read as "one request at a
time" and the tools were withheld from a session with three places to run.
It counts the nodes now, and when it does withhold, it names the node
capacities rather than telling you to raise a setting that was not the
binding one.

**Configured agents never consulted the nodes.** `spawn_agent` placed;
`subagent_<name>` — the agents defined by a file in `.cline/agents` — gated
against the session's single endpoint instead. They place now, unless the
agent's own file names a provider or profile, in which case it stays where it
asked to be. The node lease is returned however the run ends.

**And two nodes on one server are two lanes, not one queue.** A placed agent
ran inside its node's lease *and* a shared per-endpoint gate, and that gate is
one object per endpoint — so every node capacity on a shared server was
decorative. Two nodes on one endpoint are two of its slots; how many requests
it takes at once is its own answer, and its refusal is the backstop.

A node nothing can connect to now leaves the rotation for 30 seconds and
rejoins by itself, so one unplugged box is not a connect timeout on every
spawn. Being unreachable is read narrowly — a rate limit, a rejected field, a
context overflow and a model error are all servers that answered.

## The chat can tell you what the agents are doing

Agents defined by a file arrived as a bare line:

    Cerebriline used `subagent_js_syntactic`:

No name, no colour, no prompt, no stats. The rich sub-agent row existed the
whole time and was reachable only by `spawn_agent`; a configured agent missed
it at all five places it is decided. It now gets the same row, named for what
it is — `js-syntactic`, not `subagent_js_syntactic` — and says which node it
ran on.

Above the conversation there is now a strip of the agents working right now,
one spinner each so a queued agent and a working one are not the same thing,
with the node it is on and the tool it is running. Clicking one opens what it
was asked to do. It closes itself when the agent finishes.

What each agent is doing had never been reported by anything: the field the
row displays was declared, parsed and rendered, and no code ever wrote to it.

## An edit that named a line and quoted part of it

    {start_line: 90, old_text: "}});});}", new_text: "}});}"}

Line 90 was 300 characters of minified JavaScript and `old_text` was its last
eight — exactly the characters the edit meant to change. It was refused.

Neither half was wrong. The range said which line, the anchor said which
characters, and the tool had no reading that used both: it could either
replace the whole line, deleting the method, or refuse. It now intersects
them. The anchor must appear exactly once inside the range, and is never
looked for outside it — the range is what makes a fragment like `}});});}`
mean one thing in a file full of them.

An edit whose line numbers have gone stale still moves to where its anchor
actually is, as before. This only catches what that leaves refused.

## The settings panel showed the wrong node

Loading an API configuration profile left the panel showing the previous one
until you switched to another node and back. A second case did the same to
ordinary edits: a value typed into a node's settings could be overwritten by a
snapshot a round trip behind it.
